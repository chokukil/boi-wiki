# SVID semantic construction

Use existing `boi/svid-native-interpretation@1` and common semantic descriptor contracts. Extend their declared fields and relations; do not introduce a parallel ontology or infer a canonical taxonomy from one source's prose.

- Distinguish source-record identity, catalog namespace/model/SVID, parameter name, component definition and physical instance. Keep repeated identifiers as separate source records. Compare descriptions and scope before proposing evidenced equivalence, aliases or conflict.
- Identify quantity, role, value type, measurement procedure and component. Actual readback, setpoint, controller output, computed diagnostic, categorical state, identifier, count and timestamp differ. An analog input suffix does not make a controller-output reading a measured temperature.
- Compare existing concepts before creating new ones. Link measurement/setpoint, independent signal origins, calibration result/event/time, and derived metric/inputs only when source evidence establishes the relation. Shared words, proximity and path syntax do not prove business relationships.
- Keep observed value, default, example, range, configured threshold, diagnostic class and storage limit distinct. Preserve each assertion's conditions, units, time and exceptions. An implication is not its converse; overlapping intervals do not establish precedence.
- Separate literal unit labels and interpreted unit semantics. Computational units require read quantity/unit definitions and pinned revisions. Unitless categories differ from missing units. Preserve absolute/interval and time semantics; signal level alone does not establish gauge/absolute pressure reference.
- Reuse a suitable `kind: quantity` concept in an exact `boi/common-meaning@1` revision through `quantity_kind_ref: <revision ref>#/concepts/<index>`. Read its definition, evidence, conditions and limitations first. Its optional `quantity_dimension` is an explicit interpretation, not an inferred label. A declared computational unit must match that dimension. Include the read quantity and unit revisions in new dependencies and the existing-knowledge comparison; the server retains their review/explanation/execution requirements. A shared quantity never merges device, module, role, procedure or time. Legacy observation-local quantity references remain readable and are not evidence of shared-definition reuse.
- Ground each description independently. Preserve conflicting identities, units, bounds and stronger translated claims. Correction ledgers report transformations, not verified truth.
- Bind relations and owned condition/exception/counterevidence closure to exact meanings and quotations. Cross-record quotation use preserves both full record contexts; it does not itself establish identity or inherited conditions.
- Review the full applicable source for omissions while qualifying supported nodes. Unresolved explanations need not erase supported identities; unresolved executable roles/units still prevent execution. Repair affected revisions without re-extracting whole sources.
- For a correction to unchanged source bytes, submit the exact current interpretation with only the intended meaning changes, retaining its original evidence and source provenance. The server can verify unchanged fields across parser projections without rewriting old references. Do not mix a new parser's span ID into a quotation using the old projection, or replace the extraction digest with a guessed value. Inherited typed unit/quantity dependencies are read again under current access; new or replaced references need explicit comparison. A changed unit replaces only that descriptor's unit requirement, preserving other uses and unresolved conflicts.

Test reuse across unseen descriptions, paraphrases, components and roles. Keep known examples as regression evidence. Ingestion must not receive answers, selected correct parameters or expected judgments. Report source fidelity separately from scientific validity and metadata separately from live binding.
