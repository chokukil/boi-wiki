# Domain package authoring and qualification

Use this reference when repeated work needs reusable domain guidance or a team package change. The external agent performs the API work from the user's request; users need not assemble manifests, evaluation receipts or developer payloads. Discover the connected server's contracts before acting. Package qualification currently covers fixed reference checks, not general semantic quality or deployment approval.

## Start from supported knowledge

For a new domain, continue source-grounded assetization with the common package and `boi/common-meaning@1`: preserve concepts, claims, relations, conditions, exceptions and evidence; compare existing definitions before splitting, relating or revising them. Explain the specific missing domain responsibilities. A new name alone does not justify another package, and a package cannot add a content contract or operation that the server does not support.

Call `boi_domain_packages(operation="discover", request=...)` in the actual authorized team scope. Read the relevant exact package revision and its resources with `read`. Discovery returns `contracts.manifest`, `contracts.evaluator_observation` and `hotl`. For `hotl.available=false`, preserve useful common work and an ordinary unqualified package proposal when its content and sharing are permitted; report the returned reason. Do not claim qualification or invent an evaluator, policy, team membership or permissions.

## Author a candidate against fixed criteria

1. When HOTL is available, call `freeze_policy` with `team_id` and an idempotency key. Retain both its exact `revision` and returned `policy`. The server fixes allowed operations, content contracts, tool revisions, independent evaluator identities, case input/result digests and trial limits. Do not rewrite criteria after seeing the candidate's results or copy expected results into an evaluation output.
2. Read existing pack/profile/skill/harness/tool assets and original sources using the normal catalog and exact knowledge/context reads. Reuse appropriate revisions. Prepare and acknowledge the actual task knowledge context with `boi_task_knowledge_prepare`, `page` and `ack`; never claim unread pages. Use the existing authorized namespace and sharing context rather than inventing another tenant.
3. Author a declarative `boi/domain-package@1` manifest under the discovered schema: stable package ID, purpose, version, instructions, supported operations, content contracts and exact member revisions. Instructions should describe source intake, comparison and reuse, semantic splitting/relations, conditions/evidence, review/repair and later retrieval for this domain. Declare members as asset dependencies and preserve their transitive source rights. Submit an ordinary `kind="pack"` candidate with `boi_knowledge_propose`, actual sources/evidence, acknowledged reading reference and idempotency key. Changed content needs the previous revision; retain the returned package revision. No code installation, executable registration or privilege expansion is part of this step.
4. Call `create_candidate` with `team_id`, `policy_revision`, `package_revision` and a fresh operation key. Keep its candidate `revision` and exact `assessment_inputs.evaluation` / `assessment_inputs.trial`. These named proposal inputs bind evaluation to this candidate and frozen policy; pass their returned `content_json` unchanged. Recreating the same candidate with a new key does not discard failed or unknown runs.

## Obtain actual evaluation and trial evidence

Use an already registered, policy-allowed shared harness and independent evaluator. Read the exact harness stage and declared input names. Through `boi_domain_work(action="start")`, supply that harness revision, stage ID, original case sources, acknowledged context and named inputs: the actual candidate asset revision, the exact phase assessment input and the configured case input bytes. All must be the material actually delivered to the evaluator; matching labels alone are insufficient.

Use the returned TaskPackage's claim and `boi_tool_execution` prepare/input/dispatch/submit/evidence contracts to run the registered evaluator and retain its actual protected `execution_ref`. Follow that executor's existing transport; do not construct a signature or pretend the host's opinion is the independent evaluator. Complete the declared harness stage with its actual evidence as required. A task receipt or `complete` result is not package qualification. If no compatible registered harness, trusted evaluator or case material is available, leave the proposal/candidate unqualified and name the missing capability; common knowledge work can continue.

Call `evaluate` with the candidate revision, all recorded evaluation `execution_refs` and an idempotency key. Include failed runs and preserve pending/unknown invocations. The server verifies the full matching inventory, protected signatures, candidate and case inputs, expected result digests and declared checks; a caller-authored `passed=true` is not accepted as evidence.

Only after the server records successful evaluation, run the separate trial phase under the frozen policy. Trials must start after evaluation, use distinct runs and cover the required cases and run count. Call `trial` with all actual trial refs, then `adopt` with the exact candidate revision only when the server reports `trial_passed`. Adoption affects the selected team's package binding and rechecks current trust, rights and evidence. It does not publish code or approve all knowledge made with the package.

## Observe, correct and withdraw

Read the adopted package before admitting new work. Ordinary `read`/`discover` reports stored adoption/withdrawal state without creating an observation. Work package resolution (`resolve_for_work`) and final admission checks monitor new recorded receipts and current policy/trust; this is triggered monitoring, not a periodic scheduler or a new model run. An external monitor can record additional real evaluation evidence and call `observe` with the candidate revision, the complete matching evaluation refs and an idempotency key. Keep unresolved invocations unknown; never automatically dispatch them again. A failed verified observation can withdraw that exact adopted version. Reading a package does not resolve a user's correction or prove semantic quality.

For an authorized withdrawal request, call `withdraw` with `team_id`, exact `package_revision`, reason and idempotency key. Preserve historical results and report affected work that requires revalidation. For an improvement, retain prior evidence, revise the package and repeat qualification against the current frozen criteria; do not edit the previous version or erase its failures. Task-specific user corrections follow [supervision](supervision.md).

All package operations use native `boi_domain_packages` or public `POST /api/v2/domain-packages` with the same `operation` and `request`. Ordinary proposals use `boi_knowledge_propose` / `POST /api/v2/domain-intake/assets/propose`; evaluator work uses the existing shared MCP tools above. The portable task helper supports package discovery/reading only; it does not claim to dispatch evaluators or transport every HOTL mutation. Preserve exact request bodies and keys after an uncertain reply, recover the existing operation and do not launch another evaluation to replace unknown work. Report candidate/evaluation/trial/adoption state, evidence scope and remaining limitations separately.
