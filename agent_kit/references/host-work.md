# Host connection and knowledge tasks

The complete installed kit contains shared and domain skills, their detailed references, a package manifest and `scripts/boi_knowledge_work.py`. The helper requires Python 3.10+ standard library only. It does not import `boi_api`, start a service, dispatch a model, or require a repository checkout. Codex or Claude can perform interpretation directly through its configured native MCP connection.

Use the current `boi_bootstrap` response and actual tool schemas. `boi_knowledge_work(operation, request)` and HTTP `POST /api/v2/knowledge-work` share the envelope `{operation, request}`. The task API is an external-agent workflow: status and next instructions are stored by Wiki, while the connected agent performs the required semantic reasoning or declared tool work. Installed package capability descriptions do not attest that an unavailable server stage exists.

For a host using the portable SDK2 adapter, run `scripts/boi_mcp.py --describe-tool TOOL_NAME --state-dir private-journal` to read the current server's exact input schema through MCP `tools/list`. This operation does not execute the named tool. Follow the returned description as well as its JSON Schema: for example, a schema operation may require omitting an optional request instead of sending an empty object. A received tool error retains its bounded operational reason code as `tool_error_received`; arbitrary private server text is not printed. A protocol error or lost reply remains `outcome_unknown`. Neither state proves rollback, permits automatic mutation redelivery or grants semantic approval.

For several selected source spans, use the current `boi_source_field` batch input: `reference`, `fields: [{span_ref, offset?, limit?}]`, and optional `max_characters`. Follow the returned `continuation` arguments until null. The same input works through the official HTTP helper's `read` operation. This reads existing field projections with one source authorization per batch; it does not select meanings or re-extract the source. Keep field states, locators, original spans and Unicode offsets. On older servers whose tool schema lacks `fields`, use the existing single-field input. An empty continuation covers only the requested spans, not the whole source or its semantic interpretation.

Normal work responses use `context_view: references`. The reference projection identifies the protected context digest and exact candidate/root reads; it is not itself a complete `TaskKnowledgeContext`. New work does not select and read every search candidate automatically. Read candidates that may fit the source, compare their scope, and add the chosen revisions with `context` before context-bound authoring. Required semantic dependencies remain resolved; only verified optional workbook-navigation inventories are deferred to the existing source reader. If the selected process validator or other consumer needs the complete bound context, follow `full_context_read` or request `context_view: full` on the outer MCP/API envelope. The installed helper accepts `--context-view full`. This read never requests another attempt or resets a budget. Historical full contexts and their digests remain recoverable when context is explicitly expanded.

## Continue a task

For a title/description correction with unchanged source and semantic content, the current work schema supports `operation: revise`, the exact read `target_revision`, and `retain_target_content: true`. Supply the new title, description and reason; omit content, evidence and dependency replacements. The server retains the authorized immutable target's content, source evidence, dependency roles and revision relations, then performs the usual record, context, source, current revision and domain checks. Keep record outcomes, source comparison and any additional revision-scope context explicit. This option does not validate the new prose or permit a semantic correction; use the full revision contract for changed meaning, units, conditions or references. If the current server schema lacks this option, follow that server's full revision contract. Running tasks keep their pinned package versions.

- `status`: send the opaque `task_ref` from Wiki. Inspect source/package revisions, current progress and unresolved attempts.
- `resume`: restore that task by `task_ref`; do not recreate its work from a previous conversation.
- `next`: send `task_ref`, current `expected_revision` and a stable `idempotency_key`. Follow the returned operation, selected context and output schema. Do not infer that a next instruction is completed work.
- `context`: when additional catalog/read results are needed, send the current `task_ref`, `attempt_ref`, `expected_revision`, exact `revisions` and a stable `idempotency_key` before submitting. Read the returned expanded interpretation context and its new digest; use only those pinned definitions in a context-bound proposal. Catalog ranking does not limit which authorized definitions can be compared.
- `output`: read a retained attempt by `task_ref` and `attempt_ref`. Follow `offset` and `limit` until `next_offset` is absent to recover its exact original output, structured result, validation error and already published references. Readback does not repeat execution.
- `submit`: send `task_ref`, the returned `attempt_ref`, a stable `idempotency_key`, the actual structured `result` and required nonempty original external `raw_output`. Read `result_schema`; its source-grounded changes distinguish reuse, create, revise, conflict and unresolved work. Exact asset/evidence references refer to work actually read or performed. No agent-generated receipt substitutes for a required registered executor receipt.
- A `produced` result accounts for every exact `record_locator` in the attempt through `record_outcomes`: `assetized`, `context_only` or `unresolved`, with a reason and actual applicable `change_ids`. Context-only records are retained context, not invented meanings. Unresolved records remain gaps. A recorded output is not a semantic approval. A `validation_error` retains the original failed output; inspect that reason and deliberately retry within the remaining task budget before producing corrected work.
- Each change must cite the records that its accounting says it handles. Include every actual quotation span in `evidence_spans`; merely listing an own-record span while quoting only other records does not establish coverage. Explicit extra source context is allowed alongside primary-record evidence. A `reuse` change also supplies the current source record's comparison evidence; the existing definition alone does not account for newly supplied material. An unresolved change cannot mark a record assetized. Current-use targets and their dependencies must still be current at publication; historical reads and exact recovery of already committed outputs remain separate.
- `reconcile`: after recovering the original output of a recorded `unknown` attempt, send its `attempt_ref`, current `expected_revision`, a stable `idempotency_key`, `recovery_reason`, actual `result` and original `raw_output`. This preserves the unknown record and a bounded recovery lineage. It does not authorize rerunning an unknown invocation or manufacturing a replacement output.
- `schema` and `list`: use an empty request to discover current operation schemas and `content_schemas`, or the user's current tasks. Author content from the actual selected supported schema; do not infer required fields from a contract name.
- `retry` and `stop`: use the current schema, task revision, reason and idempotency key. Retry is a deliberate state transition permitted by the retained task budget; it is never automatic recovery of an unknown execution. Preserve stopped work.

Treat returned schemas as authoritative. Preserve all unknown executions and raw failures. After a transport timeout, read task status before reconciling the same admitted attempt. Do not request a new attempt or rerun the model to discover whether an earlier submit succeeded. The helper makes one HTTP call and never retries automatically.

## Start from material

Find current authorized source identity before capturing duplicate material. Use existing `boi_source_capture` for new bytes or the helper's `capture` operation. Supported XLSX uses the current file-source contract up to 16 MiB; supported text/CSV/JSON/YAML/SQL uses the inline contract up to 65,536 bytes. Other content needs an available connector snapshot or supported source reader; do not claim unsupported files were interpreted.

Knowledge registration prepares a reusable candidate index. Normal `boi_knowledge_catalog` queries and exact `reviewed_definition` lookups read this index and the requested page; use the returned candidate meanings and their exact source/review readers to decide suitability. `searched_asset_count` is the authorized indexed corpus size, while `candidate_projection_reads` counts the candidate projections read for this page. Neither number establishes semantic recall or answer quality. Use `purpose: history` explicitly for old requests, answers and evaluations.

If a catalog call returns `DOMAIN_SEARCH_INDEX_NOT_PREPARED`, first inspect the current tool schema and the request's `purpose`, `target_space` and namespace. Omitting `target_space` selects the owned native asset path; a published knowledge lookup must use the actual intended space and its supported purpose. Do not perform maintenance to compensate for choosing the wrong catalog path. If explicit index preparation is required for the task's already discovered native scope, use `boi_knowledge_catalog(prepare_index=true, namespace=the actual discovered scope)`, without a query, cursor or review target. An unknown namespace is a scope gap: do not omit it and prepare every namespace. This preparation rebuilds a disposable index from existing current knowledge and sources; it does not rerun interpretation, reingest the workbook, approve knowledge or consume a semantic repair attempt. Keep this preparation separate from measured normal questions. A current permission error or concurrent revision must be resolved from actual state, not hidden by an empty search result. The installed HTTP helper supports the same arguments through `read --tool boi_knowledge_catalog`.

Context preparation and current review/answer reuse use this same index for the exact definition inventory and incoming declared conflicts/supersessions. They can therefore report the same preparation error after an index format change; repair the derived index and retain the original task, review, package pins and attempt budget. Selected dependency checks do not establish that no relevant unlinked material has appeared: perform current candidate discovery for the question as well. Native composition preparation/read responses include `runtime_observation` with server-operation time and catalog store-call counts. These are not external-agent/final-answer latency, embedding counts or semantic validation, and are not part of the stored answer's authority.

After original-byte capture and digest readback, `start` accepts `request_text`, actual `sources` artifact envelopes, selected `package_ids`, optional authorized `team_id` and a stable `idempotency_key`. A changed source may explicitly link `previous_task_ref` to preserve prior useful work. Omit package IDs to use the server's common default when domain selection is unresolved. Its `boi/common-meaning@1` source-grounded representation supports novel-domain claims and relations without claiming specialized execution. Select package applicability from actual content, never filename or keyword rules. Namespace and identity come from the server, not request text.

Read source fields and the task-selected package instructions before reasoning. Complete source preservation, comparison/reuse, meaningful splitting/relationships, conditions/evidence, bounded review/repair and discovery/use as supported by the returned task plan. Record any unsupported domain stages as gaps. Preserve already useful meanings and original sources rather than forcing all material into a known domain.

## Metadata discovery and use

Store meaning and metadata in the chosen package's existing content contract and the same task result. Compare current definitions before reuse, evidence reinforcement, revision, conflict separation or creation. Describe the actual item in `changes[].description`; do not repeat a processing or review notice across unrelated items. Support names, aliases and descriptions with the source and exact existing definitions. Unknown, not applicable, contradictory and unreviewed are separate from a content description. The server validates references and quotations; source fidelity still requires external judgment.

For a description correction, read the latest asset and retain its meaning content, evidence and declared semantic relationships. Submit a revision against that exact target. An unchanged submitted meaning/source payload preserves its existing dependency roles, conflicts and supersession links; normal quotation, source-record and current-dependency checks still apply. Do not remove or replace dependencies merely to shorten the request. A semantic/source/dependency change needs the corresponding explicit comparison and supported revision contract.

Candidate discovery combines names and descriptions with existing evidence-owner meanings. After interpreting the request, optional `meaning_query` on `boi_knowledge_catalog` can read exact stored properties. Each condition has `owner_pointer` (an existing meaning pointer, or `*` across evidence owners), `field_pointer` (a JSON pointer relative to that owner), scalar `value`, and `basis` (`explicit` from the request or `inferred` by the agent). Obtain field semantics from the selected package contract or an exact meaning read. Do not invent unseen IDs, translate unit labels mechanically or case-fold units. The connected agent constructs these arguments; the user supplies their natural request.

These conditions expand and order candidates independently. They are not a conjunction, applicability verdict or exclusion filter. Keep a natural query alongside them so unknown or differently expressed metadata remains discoverable. `property_matches` shows the exact owner, field and value that matched; `metadata_read` reads its exact revision. Missing metadata, no exact match, unprepared index, restricted access and missing source information are different states. This interface does not yet provide sentence embeddings or a semantic-recall guarantee.

Read selected meanings with their owned conditions, exceptions, counterevidence and dependencies before explaining or calculating. A quantity or unit label in a candidate cannot establish a typed Formula input, valid measurement procedure, freshness or a live binding. Use the existing qualified parameter/unit and protected Formula path for actual calculation.

On publication, inspect both the saved revision and `projection_status`. Deferred preparation preserves the knowledge output; recover the derived index without repeating completed interpretation. Pin package and source revisions throughout a task. For an evaluation, fix required meaning and evidence before the question, then separately record discovery, additional reads, final meaning use, actual execution and elapsed time. A schema pass, candidate match or smaller response is not semantic success. Keep known cases distinct from unused questions.

## Updated material and retained work

Start an update with the prior `task_ref` as `previous_task_ref` and the current captured source references. For several replaced sources, provide explicit `source_revisions` pairs of `previous_artifact_ref` and `artifact_ref`; these declare document revision lineage, not equipment, parameter or concept identity. A single replaced source can be paired automatically. Resolve an active or unknown parent attempt before starting its update.

For each produced result, declare the scope of interpretation in `revision_scope`. The conservative default `basis: whole_source` retains a dependency on the whole original. Use `basis: declared_records` only when interpretation is bounded to the assigned records plus all actual supporting context in `context_spans`. Quoted change evidence is also retained as a dependency. Headers, unit definitions, applicability notes and contradictory passages can affect otherwise unchanged rows. Do not narrow this declaration simply to obtain reuse. Keep `order_sensitive: true` for sequence-dependent work; use false only when row ordering has no semantic effect. A process block moving as a whole can change its sequence even when the steps within it are unchanged.

Read `source_delta`, `record_lineage`, retained results and `budget_remaining`. Exact structural correspondence can preserve a completed unit's original asset revisions, quotations and output without creating new knowledge. It does not prove business identity, semantic correctness or a new source endorsement. Uniquely matched records can move; identical duplicate rows remain ambiguous. Changed, removed or unmatched records require comparison with the affected prior knowledge. Do not infer equivalence from an SVID number or filename, or silently replace original evidence with a new cell address.

If `next` returns `revision_impact`, compare the listed original records and affected prior results before submitting. Include `revision_impact_review` with disposition `reviewed` and the actual reasoning, or `unresolved` with the remaining gap. Record any necessary knowledge revision separately; reporting a review is not a server quality verdict. A deleted source statement does not by itself make a claim false, and other valid evidence can remain usable. Completed units stay complete only while their exact dependencies remain usable.

Resuming, branching or changing package versions retains consumed work and shared repair allowances. Read task status and retained output after a lost submission response. A recorded `submitting` attempt can restore the identical retained submission; an `unknown` attempt uses `reconcile` as described above. Neither case authorizes a new model invocation to recreate its output. An already committed SVID or common-knowledge revision is recovered through its original server publication identity.

## HTTP helper

Configure `BOI_BASE_URL` with the user's service origin and keep the existing personal token in `BOI_PAT` (or use `--token-env` with another environment-variable name). Never put tokens in commands, files, reports or chat. The helper rejects redirects and never forwards authentication to another origin.

Run the helper from its installed absolute path; examples below are relative only to the installed kit directory:

```bash
python3 scripts/boi_knowledge_work.py status --task-ref TASK_REF
python3 scripts/boi_knowledge_work.py resume --task-ref TASK_REF
python3 scripts/boi_knowledge_work.py next --request-file next-request.json
python3 scripts/boi_knowledge_work.py context --request-file additional-definitions.json
python3 scripts/boi_knowledge_work.py output --request-file retained-output-page.json
python3 scripts/boi_knowledge_work.py submit --request-file completed-output.json
python3 scripts/boi_knowledge_work.py reconcile --request-file recovered-original-output.json
python3 scripts/boi_knowledge_work.py schema
python3 scripts/boi_knowledge_work.py read --tool boi_source_field --request-file field-request.json
```

The JSON request files contain the exact current request object, without the outer operation envelope. Agent tools author these files from actual server schema and outputs; end users do not need to assemble them. `--request-text`, `--sources-file`, `--package`, `--task-ref`, `--expected-revision`, `--attempt-ref`, `--result-file` and `--idempotency-key` are convenience inputs and cannot override conflicting fields in a retained request file.

HTTP-only hosts use `read --tool` for the exact current requests of `boi_source_project`, `boi_source_field`, `boi_knowledge_catalog`, `boi_knowledge_read`, or read/discover operations of `boi_domain_packages`. Follow source offsets and catalog cursors until the needed scope is complete, and retain original span/revision references. These endpoints mirror source/asset read contracts; the helper does not guess content or select semantic candidates. Other execution tools use the configured native MCP surface and current registered executors.

Capture an original file with explicit media type and idempotency key:

```bash
python3 scripts/boi_knowledge_work.py capture --source-file SOURCE.xlsx --media-type application/vnd.openxmlformats-officedocument.spreadsheetml.sheet --idempotency-key CAPTURE_KEY
```

The helper records request digests, exact task requests and received outputs in private files under `BOI_WORK_STATE_DIR` (default `~/.local/state/boi-wiki`). Capture journals record the original digest and key rather than duplicating file bytes. Journals are local provenance, not current authorization or task truth. A response marked received is not a semantic completion verdict. Use `--state-dir` for an explicitly chosen host journal location.

## Package and server compatibility

Common quantity definitions use existing `boi/common-meaning@1` concepts with `kind: quantity`, a stable concept `id`, an evidence-bound definition and optional `quantity_dimension`. Use the current content schema. Declare a dimension only when the source and domain interpretation establish it; absent dimensions remain unresolved. Compare existing definitions before creating another one. SVID references the exact revision plus `/concepts/<index>`; compatible Formula previews consume this protected dependency and compare its dimension with the resolved unit. This is a candidate structural check, not scientific verification, a measurement, or approval of every claim in the common definition. Conditions and limitations remain part of the quantity read.

For Formula, reuse exact `unit_definition_reviews`. If an unchanged unit's legacy review is blocked by a changed namespace inventory, preserve that review and inspect the new current definitions. Use existing task-knowledge prepare/page/ack with the unit's actual namespace, the review's sources and `definition_reading: all`. Compare the delivered definitions for applicability and conflicts; delivery alone is not this judgment. When the current Formula schema supports `unit_definition_readings`, attach that acknowledged reading under the same unit ID. The server checks the exact original unit and dependencies against this current protected scope, preserving the original opinion. A changed unit, incomplete/other namespace reading or competing declared unit ID cannot use this path. This refreshes current knowledge delivery, not semantic review or authority. New unlinked definitions still require reading; do not bypass a scope failure or regenerate the unchanged unit/review. Current complete-scope checking can remain costly; report its actual calls separately from answer latency.

`package.json` lists domain packages and existing content contracts. Repository-relative `skill_path` values identify package source; within the installed kit remove the `agent_kit/` prefix to resolve them. Current server task snapshots pin the resources they actually use. If the returned task requires a missing or different contract, preserve that mismatch before model work and update the installed package or continue supported independent work. Do not fall back to old `boi_agent` instructions.

Starting with a domain package also selects its declared shared dependencies. The returned `package_selection.packages` binds each exact revision and its own `resource_digests`; `dependency_manifest_digests` binds the content of required packages, including their references. Read an instruction or linked reference from its owning package with `boi_domain_packages` read, supplying that package's exact `revision` and `resource_path`. A link into common guidance uses the pinned common package. An installed copy may be used only when its bytes match the returned digest; a newer distribution does not replace a running task's instructions. Undeclared references, missing resources, dependency cycles and incompatible dependency versions fail before new work. These structural checks do not establish semantic qualification.

Package file verification establishes complete local installation, not authenticated server availability, semantic accuracy, scientific verification or live equipment access. Final acceptance also needs a fresh configured host to perform actual supported work and open the resulting Wiki knowledge and sources.

## User correction and supervision

Read [the supervision contract](supervision.md) when a user reports wrong source interpretation, omitted coverage, an unsuitable definition or asks to stop work. `boi_knowledge_supervision` and the helper's `supervision --action` use exact task, unit, asset and event references. Pending instructions returned with a task must remain visible until their handling is explicitly reported. Reading an instruction does not resolve it; reporting it resolved does not establish semantic quality or authorize new execution.
